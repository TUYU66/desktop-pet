# 本地音乐插件与网页管理

## 使用

1. 音乐初版需要 Java 音乐接口。此次音量与唤醒交互更新需重启 Python、更新网页，并自行编译烧录 ESP32 固件，以显示音乐状态和音符表情。
2. 左侧导航进入“音乐空间”，上传 MP3（单首最大 32 MB）。
3. 选择在线小智，点击歌曲旁“播放”。音频从小智扬声器播放，网页不播放音频。
4. 页面支持暂停、继续、上一首、下一首、停止、删除，以及 0～100% 独立音乐音量。正在播放的歌曲被删除前会停止。
5. 可语音说“播放某首歌”“暂停音乐”“继续播放”“上一首”“下一首”“停止音乐”。没有添加语音查询曲目功能。

文件保存在 Python 的 plugins.play_music.music_dir（默认 xiaozhi-python-server/music）。相对目录始终相对 Python 项目根目录。
文件按“歌手-歌名.mp3”命名，例如“周杰伦-彩虹.mp3”。以第一个半角连字符拆分歌手和歌名，自动去除两侧空格；歌名可以包含连字符。没有有效分隔符时保留完整文件名作为歌名。歌手名字含连字符时请调整命名以免拆分歧义。
已有的“歌名-歌手.mp3”文件需改为新顺序，否则页面会把歌手和歌名显示对调；本次已调整仓库音乐目录中两首旧顺序文件的名称。
支持仅歌名或完整文件名精确匹配及包含匹配；多首匹配会要求更明确的歌名，不随机猜歌。列表按文件路径排序，上下首循环切换。歌曲自然结束后自动顺序播放下一首，最后一首回到第一首。
网页可搜索歌名，重名上传拒绝覆盖。上传以临时文件接收，经 ffprobe 验证确实为 MP3 后才加入音乐库。

## 播放行为

音乐独立于 TTS 文本队列，由 FFmpeg 逐帧解码为单声道 PCM，再按已有设备音频协议发送 Opus。
暂停保存当前服务器发送进度，继续时从该位置解码；页面进度是估算，包含设备预缓冲影响，并非设备采样级回执。
网页文字直接临时暂停音乐后处理聊天或动作，保留歌曲进度，不再询问是否停止音乐并聊天；明确要求继续播放的文字保持音乐播放并仅在网页确认。唤醒和到期提醒也会临时暂停歌曲。结束后不会自动续播，可在网页或语音继续。
歌曲播放期间独占当前连接的聊天锁，切歌先停止旧任务再启动新任务；断开连接清理进程及播放任务。
网页暂停/停止会让支持待机协议的设备回待机；唤醒打断只临时暂停，不发送待命指令，设备询问“想暂停、继续播放，还是切换上一首、下一首？也可以调整音乐音量。”，然后聆听用户操作。没有回答时仍使用原有会话超时，不自动续播。
新固件收到音乐标记显示“播放音乐”，使用笑眼、唱歌嘴型和持续上浮音符；停止、聆听后退出。表情动画并非实际音量/节拍分析。
音乐音量默认70%，只对音乐 PCM 做缩放，0%静音仍继续播放，不改变设备主音量与 TTS 响度；设备主音量仍决定最终响度。可语音指定“音乐音量调到50%”。音量只在本次设备连接期间保留，重连后恢复默认。
播放进度只在当前设备连接期间保留；重连或重启不恢复，MP3 文件保留。

## 依赖与服务

Python 运行环境需要 ffmpeg、ffprobe 和现有 opuslib_next/原生 Opus 库，沿用项目音频依赖。
Java 已登录接口 /xiaozhi/api/music 代理 Python /xiaozhi/music；MP3 上传采用流式传输，不以 JSON/Base64 缓存在 Java 中。
默认 Java/Python 同机部署，内部音乐接口只接受回环地址且要求 Service-Key。分机部署需在两端设置相同的 XIAOZHI_MUSIC_SERVICE_KEY。
音乐库与当前项目的设备管理一致，为本服务共享音乐库，未实现多租户私有曲库。

### 播放启动与自动聆听回执

播放工具会先排队等待上一轮 TTS 收尾。音乐 loading/playing 期间，普通自动 listen:start 和待命回执不作为暂停命令；真实唤醒 abort、明确 detect、按键 manual 和聊天输入仍可打断。播放器等待 TTS stop/standby 全部发送完成后再启动，避免上一轮结束消息覆盖音乐开始消息。
此修复仅涉及 Python，重启服务后验证语音“播放音乐”、网页播放、下一首及音乐中唤醒。成功开始发送音乐时会记录“音乐开始播放”日志。此次未执行编译或运行测试。

### 音乐控制对话收尾

唤醒后的操作询问仍保持聆听。音乐命令成功后播报确认，等确认语音结束再退出聆听：暂停、停止和音量设置回待命；播放、继续和上下首则在收尾完成后进入音乐播放状态。操作失败仍可继续补充歌名或参数。此次只修改 Python，未运行测试或编译。

音乐唤醒兼容两种明确通知：abort(reason=wake_word_detected) 和 listen:detect。收到后立即停止歌曲并询问，不再依赖后续 listen:start 触发询问。同一次询问发出后的五秒内，同一 sentence_id 的重复 detect 不再进入普通问候；新对话更换 sentence_id 后不受该去重影响。日志应出现“音乐唤醒：已暂停歌曲，询问播放操作”。这次分支修复未做运行验证。

### 切歌与回复收尾的轮次隔离

语音/网页文字工具触发的播放、继续、切歌绑定本轮 sentence_id，收到该轮 LAST 完成通知后才允许启动解码。不能用队列暂时为空判断回复已经结束（文本可能已被工作线程取走，仍在合成）。网页播放器按钮不等待不存在的确认语音。切歌取消旧等待任务并创建自己的等待条件；等待回复最多60秒，超时在网页状态中报告错误。

TTS、字幕和待命消息携带 stream_id。服务端在等待音频完成后重新核对轮次，过期 stop 不清除新流状态；新固件在音乐播放期间忽略其他轮次的 stop、standby 和字幕，以及聊天表情。音乐启动日志包含排队歌曲与等待轮次，便于区分“命令已接收”和“已开始发送音乐”。

## 当前交互修复（以本节为准）

- 明确的播放、上下首、暂停、继续、停止命令在进入通用聊天模型前直接执行本地曲库操作。确认语来自执行结果，不使用模型猜测歌名；其他表达仍可能需要模型理解。
- 播放期间麦克风音频不作为聊天输入处理，设备保留本地唤醒检测和音乐表情。用户唤醒后临时暂停并询问操作，操作确认结束后退出聆听。
- 网页音乐命令直接处理；其他文字临时暂停歌曲后直接处理，不再要求确认。语音中的音乐聊天确认仍限当前会话，120秒有效。
- 顺序循环：自动播放下一首、手动最后一首切下一首均回到第一首，只有上传曲库中的文件可以播放。
- 修复 WebsocketProtocol::EnterStandby 将逻辑待命误报为物理音频连接关闭的问题。此前延迟回调会在新歌开始后把显示切回 idle。待命保留连接时不再调用物理关闭回调。
- stop 消息明确携带 listen_after；操作完成直接待命，不先开启一次聆听。播放期间显示音乐表情，待命在此指不接受普通麦克风输入、仍可用唤醒词，不是显示普通待机脸。

这次涉及 Python、Java 聊天结果转发、前端提示与 ESP32 固件，均需更新后验收。新增路由及确认回归用例，未运行编译、测试或烧录。重点验收：连续三次唤醒下一首、网页文字切歌、最后一首回第一首、自然结束自动续播、普通聊天确认前音乐不中断、暂停确认后不再聆听。

### 2026-09-30 网页文字暂停被上一条请求拦截

网页文字音乐指令的确认语音结束后，立即将请求回执更新为处理结束，不再等请求等待任务退出后才更新。若播放器已经进入 playing，且所等待的确认轮次和上一条请求的轮次、会话相同，则允许释放上一条请求的占用；仅处于 loading 或轮次、会话不同仍保持拦截。原请求收尾时不会清除新请求的跟踪对象。
