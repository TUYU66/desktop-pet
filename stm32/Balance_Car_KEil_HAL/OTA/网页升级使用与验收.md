# STM32 网页 OTA 使用与验收

> 2026-11-09 更新：下文原有首次烧录与演练目录为历史验收记录。日常发布请在项目根目录运行 `python stm32/Balance_Car_KEil_HAL/OTA/tools/build_stage1.py`，自动生成递增版本并写进应用；上传 `firmware-releases/stm32/版本/application-ota.zip`。新版描述符同时校验内部版本和清单版本，不能把同一应用随意改版本重复打包。
>
> 当前支持网页手动更新及机器人启动时自动检查新版。自动更新需要新版 ESP32 与底盘的真实版本播报；旧底盘先手动升级一次。读不到版本时不自动刷写；原有停稳、电压及完整性检查不变。本轮只更新应用即可，不要求重刷已有 OTA Bootloader。ESP32、Java、Python 都需要运行本轮新版，静态前端需更新构建产物。

## 当前状态

代码已实现：网页上传 STM32 ZIP → Java 校验并保存 → 管理员发起升级 → Python 调用
隐藏操作工具 → ESP32 下载原始 BIN、校验并缓存 → 退出 BLE/坐下 → STM32 进入 Bootloader
→ UART 分包传输 → 校验安装 → 复位并确认应用遥测恢复。

此前用户已完成网页升级到 2026110404，并确认页面显示“升级完成，设备已启动”。
本轮新增恢复入口、500ms 普通启动窗口和发布检查；这些新增行为尚需实机验收，不能用主机测试替代。

开发验证：上一轮 STM32 普通恢复、Bootloader、OTA 应用均为 0 错误、0 警告；ESP32、Java、前端构建通过。
本轮 Bootloader 7,132 字节，OTA 应用 85,360 字节。旧的网页包缺少本轮发布描述符，
新版上传校验将拒绝它们，请使用下面的新 ZIP。

## 一次性安装

1. 用 ST-Link 烧录本目录对应的整包：
   `D:\study\bishe\firmware-releases\stm32-ota-hardened-20261104\factory-stage2.hex`。
   文件名沿用 stage2。本轮修改了 Bootloader，必须再用 SWD 烧录一次这个新整包；仅网页更新应用不会更新 Bootloader。
   **不能继续使用之前串口轮次目录的同名 HEX。**
   使用工具的正常擦除写入流程并启用写后校验，不跳过擦除，BOOT0 保持正常 Flash 启动配置。
2. 使用当前工程正常烧录 ESP32（原 ESP-IDF 终端进入 `xiaozhi-esp32-main` 执行 `idf.py flash`）。
   这一步安装下载和转发程序，之后普通 STM32 应用更新才走网页。
3. 沿用原启动方式重启 Java、Python 服务，让新上传接口和路由生效；前端开发服务会更新页面，
   静态部署则发布本次 `xiaozhi-web/dist` 构建产物。
4. 保持原有 ESP32 ↔ STM32 串口接线，不需要 USB-UART。确认两块板正常连接，开机约 10 秒后
   在网页账号菜单打开“固件管理”，点击“刷新进度”。

升级入口能力由 STM32 的 `DIAG,FW,2026110405,2,16383` 报告；历史非 OTA 恢复版报告 8191，页面会提示“底盘尚未就绪”并禁止发起。新能力位为 8192，约每 10 秒发送一次。

## 第一次网页测试

首次整包中的包版本是 **2026110405**。
为了演练完整流程，已准备同一应用、更高包版本的测试 ZIP：

`D:\study\bishe\firmware-releases\stm32-ota-hardened-20261104\application-web-test-v2026110406.zip`

1. 以管理员账号进入“固件管理”，选择“上传固件”。
2. 类型选择“STM32 底盘（ZIP 固件包）”，上传上述 ZIP，版本会从清单读取。
   只上传不会启动升级。
3. 在这一版本所在行点击“升级底盘”，确认后保持稳定供电。
4. 页面依次显示下载校验、准备坐下、进入升级模式、传输、安装、启动确认。
5. **显示“升级完成，设备已启动”后**，再回归底盘站立、坐下、连续动作及 BLE 控制。

“固件已安装，但应用启动尚未确认”代表安装确认已收到，但没有获得新的应用姿态/电量遥测，
不能当作整条链路成功。先查看 OLED、供电及底盘连接，不要连续点击升级。
网页刷新或 Java/Python 重启后可重新读取 ESP32 的任务状态；ESP32 自身升级中断电重启时，
会从 NVS 保留记录显示“上次升级结果未确认”，不自动重新执行旧任务。

当前页面显示的版本是升级任务的目标包版本，`DIAG,FW` 是代码能力修订号，两者不是同一个字段。
本次测试 ZIP 的应用代码相同，目的在于验证实际传输、安装和重新启动。
同一版本不能反复升级，需要重新打包更高的版本号。

## 已实现的保护

- 上传、发起、状态接口位于 `/xiaozhi/api/admin/stm32-ota/`，由现有管理员鉴权保护。
- Java 只接受两个文件的规范 ZIP，限制包/解压长度，验证板型、MCU、布局、向量、CRC32、SHA256。
  ZIP 不解压到用户提供的路径，不直接交给 ESP32 解析；ESP32 下载经过校验的原始 BIN。
- 下载授权沿用五分钟有效、一次消费的 token，响应禁止缓存；日志隐藏包含下载授权的工具参数。
- Python 接口要求设备服务私钥，且只允许一台在线设备；升级工具隐藏于手动操作通道，语音模型不能调用。
- ESP32 只从其已配置 OTA 服务的同源 STM32 下载路径取文件；Java 默认使用设备上报的该地址，
  避免自动选择电脑 VPN/网卡地址。沿用当前 Java OTA 服务地址即可，无需新增私钥。
- ESP32 在 PSRAM 中收齐并验证镜像后才开始改变底盘模式，不边联网下载边覆盖应用。
  PSRAM 缓存不跨 ESP32 断电保存；接收未完成时仍保留 STM32 原应用，重新发起时重传完整镜像。
- 自动退出 BLE、请求坐下，再等待新鲜的坐下/停止反馈。ESP32 与 STM32 都检查至少 10.8 V 的准入条件；
  该值为保守开发门限，后续仍需结合实机电源验证。
- STM32 升级入口只编入 OTA 应用目标，必须坐稳、停止、无蓝牙/转向/校准，电量数据有效。
  临界区清零 PWM、关闭 TIM8 主输出，写 BKP DR1/DR2 配对标记后直接系统复位，不在正常控制中擦写 Flash。
- 传输期间 UART 独占，普通 PING/遥测解析暂停；移动、蓝牙切换和调参/校准操作拒绝执行。
- 相同任务编号不会重新开始；每包确认会话、序号和 CRC，丢确认重发同一帧；完整镜像检查后才安装。
- 安装先提交双页日志，掉电后可由 STM32 独立从暂存镜像重新复制；尚无旧版自动回滚。
- 收到安装确认仍不会直接显示成功，必须看到复位后的新应用坐下/电量遥测。

目前是受管理员和设备私钥保护的开发链路，CRC/SHA 只提供完整性；还没有独立固件发布者签名验证。

## 服务配置与常见错误

沿用 `XIAOZHI_DEVICE_SERVICE_KEY`，Java 与 Python 必须一致，未配置会明确拒绝。
ESP32 的 OTA 地址当前应指向 Java 服务，例如 `http://电脑局域网IP:8000/xiaozhi/ota/`。
Java 默认从 ESP32 状态获取这个地址的源，构造相同源的下载 URL。
特殊反向代理场景可配置 `xiaozhi.ota.public-base-url`，但必须与 ESP32 OTA 地址同协议、主机、端口，
只填写源地址，不包含 `/xiaozhi/ota/` 路径。

| 提示 | 处理 |
| --- | --- |
| ESP32 升级工具未就绪 | 烧录本次 ESP32 固件，重启 Python 并等待设备连接 |
| 底盘尚未就绪 | 确认烧的是本轮最终目录整包、串口已连接，等待约 10 秒后刷新 |
| 下载地址不一致 / 下载失败 | 核对 ESP32 OTA 地址是否仍为可访问的 Java 服务地址 |
| 未确认坐下或电压不足 | 核对物理姿态和供电，升级没有开始擦应用 |
| 版本必须高于已安装版本 | 使用更高版本的应用 ZIP；不要上传 HEX、Bootloader 或普通地址 BIN |
| 串口响应超时 | 查看底盘和供电，等待恢复状态；不要通过连续点击重新排队 |
| 已安装但启动未确认 | 检查 OLED/串口/实机状态，保留日志，必要时 SWD 恢复 |

恢复使用完整 `factory-stage2.hex`，不单独烧录应用 BIN。历史目录里的 normal-recovery.hex 属于旧版恢复产物，新构建不再生成。

## 验收记录要求

先完成一次不中断的网页升级，再验证下载失败、重复点击、浏览器刷新、版本不递增拒绝、
传输中断电、安装中断电、ESP32 重启后的未知结果提示。每次确认恢复到坐下状态，
并回归站立/坐下/BLE。物理断电试验前保留 SWD 恢复条件。

## 本轮恢复规则（2026-11-04）

- 普通开机握手等待 500ms；应用请求进入或已建立升级会话时，仍保留 30 秒窗口。
- 安装失败但暂存镜像有效时，复位优先重新安装。持续失败时，网页恢复任务先重试 INSTALL；
  明确返回 INSTALL 错误后才尝试 ABORT。超时不会被当作明确失败后擅自切换操作。
- ABORT 仅在当前应用完整校验通过时恢复它；若候选镜像已经完整复制到应用区，则可提交候选版本。
  应用已半写且不能通过校验时拒绝取消，绝不强行启动。
- INSTALLING 且暂存区损坏时允许新 BEGIN，重传完整包。有效暂存区不会直接被 BEGIN 覆盖。
- 无法启动时每秒发送带 CRC 的 BOOT_STATE 恢复状态，ESP32 识别后网页显示恢复提示。
  恢复状态过期即失效，不允许依赖旧姿态执行移动。
- 恢复模式没有应用电压遥测，必须由用户在网页明确确认固定车体、电机停止、稳定供电。
  正常应用升级仍执行原来的坐下、停稳、新鲜电量及 10.8V 准入检查。
- 若恢复完成的版本已不低于所选固件，发出复位并明确提示恢复版本；不会伪称再次安装了所选包。
- 双页日志都损坏仍需 ST-Link 整包恢复。新增 INVALID_JOURNAL / INVALID_APP 原始串口诊断，
  ESP32 页面可通过恢复状态 0 显示日志无效。
- 发布包必须含唯一 PETOTAAPPV1 描述符、正确分区及指向实际 OTA 入口的 Thumb 地址；
  打包脚本与 Java 上传/下载复验均检查。普通工程或只改链接偏移但缺少 OTA 入口的镜像不可发布。

本轮未加入 IWDG、发布签名或旧版本自动回滚。IWDG 需同时改应用喂狗，不能只给 Bootloader 加；
TIM7 还承担校准停止保护，因此保留优先级 0，并纠正了原来写成最低优先级的注释。

建议先验证：新整包正常启动 → 网页升级至 2026110406 → 站立/坐下/BLE 回归 → 接收阶段断电。
安装阶段断电需固定车体，准备 ST-Link 恢复手段后再测试。不要为验收故意破坏真实 Flash；
暂存损坏、半写应用和日志提交断点已由主机模拟覆盖，仍需后续有计划地完成实机异常测试。
